# 07 讓 AI 看懂你的世界

## 主題
如何讓大型語言模型「看懂」使用者自己的資料:以 RAG(Retrieval-Augmented Generation)為核心,說明 embedding、文字塊切分、metadata、檢索與組 prompt 的流程;接著談 RAG 與長上下文/CAG(KV-Cache)的取捨、LLM 的短期與長期記憶;最後介紹 Karpathy 的 LLM Wiki 做法,並以「打造你的 RAG 系統」作業收尾。講者開場即強調「再度強調理解原理、不要被大字彙迷惑」[S07 p.3]。

## 重點
- RAG 被定位為「一個降低錯誤的方法」,全名 Retrieval-Augmented Generation [S07 p.3]。
- 投影片列出多篇媒體對 RAG 的討論(如「RAG 是什麼?就像是大型語言模型的『小抄』」等標題)[S07 p.4]。
- RAG 其實就是在討論 Content Engineering,有兩件事:提供需要的「正確資訊」;給「清楚的指引」,例如以上面的資訊、用什麼樣的格式與風格回答使用者的問題 [S07 p.5]。
- 講者的設問:「可以自己放、但不能叫電腦找嗎?」——資訊可以人工貼進 prompt,RAG 是讓電腦去找 [S07 p.5]。
- 關鍵是找一個 embedding 模型:把某段文字轉成某個維度的向量,這向量是該段文字的特徵代表向量、抽象的意涵;embedding 模型基本上就是一個語言模型 [S07 p.6]。
- 訓練 embedding 有時會用對比學習:問題 q、相關內容 k⁺、不相關內容 k⁻;sim(q, k⁺) 越近越好,sim(q, k⁻) 越遠越好 [S07 p.7]。
- 對比學習的損失函數寫成 ℒ(θ) = −log( e^{sim(q,k⁺)} / Σ e^{sim(q,k)} ) [S07 p.8]。
- 有些 embedding 模型會區分「問題」(query:)與「內容」(passage:)加前綴;但這種 prefix 沒有通用寫法,有些模型完全沒有使用 [S07 p.9]。
- 最傳統無腦做法:把所有檔案送進一個資料夾(如 uploaded_docs);純文字檔沒問題,PDF 或 Word 檔也都可以 [S07 p.10]。
- 最傳統 RAG 是自動把文件切成一個個文字塊(例:500 字一塊、重疊 50 字);要考慮多少字是一個文字塊、需不需要重疊,「其實重點還很多」 [S07 p.11]。
- 切分的考量包含:文字塊大小、要怎麼切(如法條是否要一條一條切)、重疊要多少字 [S07 p.12]。
- 比較新的作法是自己切成自己想要的樣子:每個文字塊包含標題、metadata(資料類型、主管機關、來源網址、整理日期)、【內容】、【檢索練習問題】、【提醒】;其中標題與內容是「做 embedding 的部份」,metadata 另外標示 [S07 p.13]。
- 實際上有兩個部份:真的要做 RAG(Embedding)的文字,以及 metadata;metadata 可以做關鍵字搜尋 [S07 p.14]。
- Metadata 是文字塊的附加資訊,例如來源(原文)、所在頁數、文章標題、作者、日期、分類等 [S07 p.15]。
- 需要 metadata 的例子:使用者想知道什麼是 AI Agents,但「不用管炎龍老師怎麼說,因為他都亂講」——此時需依作者等資訊過濾 [S07 p.16]。
- 流程:先把整理好的文件放進資料夾(rag_docs)[S07 p.17];每段文字經模型 f_θ 得到各自的代表向量 k₁、k₂、k₃ [S07 p.18]。
- 使用者下 prompt 問問題時,問題也被同一模型化為代表向量 q [S07 p.19]。
- 比較 q 與各個 k 誰最接近,找出和原本問題最接近、最相關的資料,一起放入 prompt 中;講者稱「這是近來 AI 搜尋方法」 [S07 p.20]。
- 找出的資料通常不會只有一筆,有可能需要重新排序,即 Reranking [S07 p.21]。
- 可考慮是否加入上下文或相關文章,三種做法:(1)找出的文字塊加上前一塊與後一塊;(2)找出的文字塊所在的整篇文章;(3)找出的文字塊的相關文章(相關文章 1、2)[S07 p.22]。
- 組 prompt 基本上有兩項資訊:question(使用者的問題,原始 prompt)與 retrieved_chunks(RAG 找到的資訊)[S07 p.23]。
- 例如 prompt 寫成:「請根據 {retriever_chunks} 裡的資訊,來回應使用者的問題: {question}」[S07 p.24]。
- 以上基本上就是現在火紅的 RAG 概念 [S07 p.25]。
- 反思:「全部的資訊都放 Prompt 不就結了嗎?」特別是語言模型上下文越來越長 [S07 p.26]。
- CAG:用 KV-Cache 技術把資訊都塞給 LLM;投影片引用論文《Don't Do RAG: When Cache-Augmented Generation is All You Need for Knowledge Tasks》 [S07 p.27]。
- 鍵值緩存(KV-Cache):輸入 x₁…x_T 產生 q、k、v,其中資料的鍵值(k、v)先存起來 [S07 p.28]。
- 章節 02 的標題為「記憶的一種方式」[S07 p.29]。
- 同一個系統可以用兩個以上的向量資料庫 [S07 p.30]。
- 外界常說 LLM 的「記憶」有兩種:短期記憶和長期記憶 [S07 p.31]。
- 短期記憶:就是這次和大型語言模型的對話過程;下次來,這次說的話都忘了;更糟的是對話過程太長,前面的話也會忘 [S07 p.32]。
- 長期記憶的一個做法就是做 RAG:把過去完整的對話做成向量資料庫 [S07 p.33]。
- 客製化對話機器人會記得使用者的點點滴滴(例:記得「87」常訂的餐點現在沒賣了)[S07 p.34]。
- LLM Wiki 的緣起:2026 年 4 月 Karpathy 引爆的另一篇貼文 [S07 p.36]。
- 簡單說,LLM Wiki 是打造自己的 Wikipedia:把你找的資料放進 raw,教 AI 怎麼把檔案產生/修改成 wiki 檔,wiki 內含 index.md [S07 p.37]。
- Karpathy 原文(翻譯)要點:用 LLM 針對感興趣的研究主題建立個人知識庫,token 用量更多花在整理知識(以 Markdown 和圖片形式儲存)而非操作程式碼 [S07 p.38]。
- 資料匯入(Data Ingest):把來源文件(文章、論文、程式碼儲存庫、資料集、圖片等)索引到 raw/ 目錄,再用 LLM 逐步「編譯」出 Wiki(目錄結構中的一系列 .md 檔),含 raw/ 中所有資料的摘要與反向連結,將資料分類為概念、為概念撰寫文章並全部串連;網頁轉 .md 用 Obsidian Web Clipper,並下載相關圖片到本機 [S07 p.39]。
- IDE:以 Obsidian 作為 IDE 前端,檢視原始資料、編譯完成的 Wiki 與衍生的視覺化內容;Wiki 的資料都由 LLM 撰寫並維護,作者很少直接動手修改 [S07 p.40]。
- Q&A:當 Wiki 夠大時(例:約 100 篇文章、約 40 萬字),可向 LLM 代理詢問複雜問題;作者原以為需要複雜 RAG,但 LLM 自動維護索引檔和各文件簡短摘要表現不錯,在此規模下也能輕鬆讀取重要的相關資料 [S07 p.41]。
- 輸出(Output):偏好讓它產生 Markdown 檔案、投影片(Marp 格式)或 matplotlib 圖片,再用 Obsidian 檢視;常把輸出「歸檔」回 Wiki,使探索與查詢持續累積到知識庫 [S07 p.42]。
- 檢查(Linting):讓 LLM 對 Wiki 做「健檢」,如找出不一致的資料、用網路搜尋補齊缺漏、找出有趣的關聯作為新文章候選題材,並建議值得進一步探究的問題 [S07 p.43]。
- 額外工具:作者 vibe coding 了一個簡單的 Wiki 搜尋引擎,有網頁介面,也透過 CLI 交給 LLM 當工具處理大型查詢 [S07 p.44]。
- 進一步探索:資料庫擴大後自然會想到生成合成資料並微調模型,讓 LLM 把資料「記」在權重裡,而非只依賴上下文視窗 [S07 p.45]。
- 懶人包(TLDR):收集一定數量的原始資料,由 LLM 整理成 .md 維基,再讓 LLM 透過 CLI 工具操作維基、問答並擴充內容,所有資料都能在 Obsidian 檢視;幾乎不手動撰寫或編輯維基,這是 LLM 的領域;作者認為這裡有機會打造令人驚豔的新產品,而非一堆東拼西湊的指令碼 [S07 p.46]。
- 投影片提供 Karpathy Gist 連結(bit.ly/llmwiki)[S07 p.47]。
- Farzapedia:個人化的 wikipedia 範例;畫面顯示由多年日記整理成的個人知識庫(417 篇文章、41 個分類)[S07 p.48]。
- 作業:打造自己的 RAG 強化對話機器人;程式 1「用自己的資料、建立向量資料庫」、程式 2「實作 RAG 系統」(皆為 Colab 連結)[S07 p.50]。
- 作業要求:找一個有興趣的文件(如某個規定、相機說明書);用 Vibe Coding 把數據打包成檔案(如 rag-data.zip);RAG 01 用自己的數據打造向量資料庫並打包(如 vector_embedding.zip);RAG 02 程式要能讀入並解壓縮 vector_embedding.zip;打造自己的 RAG 強化對話機器人 [S07 p.51]。

## 關鍵術語
- RAG(Retrieval-Augmented Generation):檢索增強生成,先找出相關資料再交給 LLM 生成回答,用來降低錯誤 [S07 p.3]。
- Content Engineering:RAG 的本質討論,即提供正確資訊與清楚指引 [S07 p.5]。
- Embedding 模型:把文字轉成某維度的特徵代表向量(抽象意涵),基本上是語言模型 [S07 p.6]。
- 對比學習(Contrastive Learning):讓 q 與 k⁺ 越近、與 k⁻ 越遠 [S07 p.7];損失函數見 [S07 p.8]。
- query / passage prefix:區分問題與內容的前綴,無通用寫法 [S07 p.9]。
- 文字塊(chunk)、重疊(overlap):切分文件的單位與相鄰塊重複的字數 [S07 p.11-12]。
- Metadata:文字塊的附加資訊(來源、頁數、標題、作者、日期、分類等),可做關鍵字搜尋 [S07 p.14-15]。
- 代表向量 k、q:文件文字塊與問題各自經 f_θ 得到的向量 [S07 p.18-19]。
- Reranking:對檢索出的多筆資料重新排序 [S07 p.21]。
- retrieved_chunks / question:組 prompt 的兩項輸入 [S07 p.23-24]。
- CAG(Cache-Augmented Generation):用 KV-Cache 技術把資訊都塞給 LLM [S07 p.27]。
- KV-Cache(鍵值緩存):把資料的鍵值(k、v)先存起來 [S07 p.28]。
- 向量資料庫:存放代表向量的資料庫,同一系統可用兩個以上 [S07 p.30]。
- 短期記憶 / 長期記憶:前者為當次對話過程,後者可用 RAG(過去對話做成向量資料庫)達成 [S07 p.32-33]。
- LLM Wiki:raw 資料夾 + LLM 編譯出的 wiki(.md 檔、index.md)[S07 p.37, p.39]。
- Data Ingest / IDE / Q&A / Output / Linting / Extra tools / Further Explorations / TLDR:Karpathy 貼文的各段標題 [S07 p.39-46]。
- Obsidian:作者用來檢視 raw、wiki 與視覺化內容的 IDE 前端 [S07 p.40]。
- Farzapedia:個人化的 wikipedia 範例 [S07 p.48]。
